# 故障定位与 Agent 接手指南

目标是让下一位开发者不依赖聊天历史，能复现、提出有证据的根因并提交小范围修复。先遵守仓库 [AGENTS](../../AGENTS.md) 与 [协作规范](../../CONTRIBUTING.md)。

## 一、先确认你查的是同一个版本

记录以下信息后再分析：

- Issue/维护者请求、影响的用户操作、预期结果、北京时间发生时间。
- Git 提交 SHA、维护者确认的基线/目标分支、工作区是否有别人的改动。
- 线上 `/healthz` 的 release 和健康状态；**release 字符串不是 Git SHA**，必须由发布记录建立对应关系。旧版没有 release 时记“未知”，由维护者提供部署 ID → SHA 对照；不能据此断言服务故障。
- 相关页面、脱敏 job ID、少量 record_id/商品 ID；敏感业务标识仅放受限 Issue，禁止 Cookie/Key。

若生产有模块而分支没有，先停下确认基线。不要把旧仓库与新线上行为混在一起推理。

## 二、只读排查顺序

1. **复现入口**：记下点击顺序、筛选条件、是否首次进入/刷新/换浏览器。先用 mock/测试环境复现。
2. **浏览器请求**：看 URL、HTTP 状态、响应是否 JSON；区分请求未发出、401/403、超时、服务端错误。不要分享含授权头或敏感响应的 HAR。
3. **运行中服务**：`GET /healthz` 看 Worker、Redis/PostgreSQL；`GET /api/health` 看配置。健康不证明单条业务成功。
4. **服务器任务**：`GET /api/jobs?limit=100` 找任务，`GET /api/jobs/<id>` 看状态、结果和可用进度。不要只看 localStorage，也不要因没有最终 result 就断言任务没运行。
5. **逐条证据**：分开检查视频处理子步骤、AI 文案、飞书投影和发布同步；子步骤完成不等于整条完成，不得重复计数。
6. **资源与外部依赖**：按相同时间窗口读 Railway CPU/内存、OOM/重启及网络，再对照外部 API 的超时、限流、区域和 request_id。
7. **收敛根因**：形成一个可证伪的假设。获修复授权后，才写最小失败测试并修改。证据不足标注未知，不能用“已充值”“Worker 存活”推断业务一定恢复。

只读诊断不能调用 POST 的停止、失败重试、同步、配置保存、字段创建。即便名叫“预览”，也先检查实现是否会写快照或触发外部费用。

**特别注意：** 不要在 SSH 临时 Python 里通过导入 `app` 或调用 `api.jobs.get_backend()/list_jobs()` 读取任务。这些入口可能初始化额外 Worker 并领取生产任务。查询已运行服务的 HTTP 接口即可；凭据由私密配置读取，不打印也不放命令行参数。

任务状态与逐条结果要分开看（具体版本可能只实现其中一部分）：

| 任务状态 | 意义与下一步 |
| --- | --- |
| `queued` | 已入队，检查 Worker/锁/前序任务；不重复提交 |
| `running` | 任务执行中，结合逐条检查点判断推进，不能只看最终 result |
| `retry_wait` | 后端按既定策略等待恢复，查看等待原因和时间；不手工狂点重试 |
| `done` | 整批执行结束，不等于每条成功；仍须看 success/failed/skipped |
| `failed` | 任务级异常；先查已完成检查点及外部写入是否未知，不盲目整批重跑 |
| `cancelled` | 已停止，不是可无损续跑的暂停；先确认哪些已完成/未完成 |

逐条的 `waiting_schedule` 表示账号/名额等待，不等于视频编码失败；`projection_pending` 表示结果已保存但外部回写待补，不应因此重新生成媒体。字段和恢复方式均以当前基线实现为准。

## 三、模块地图

入口先看 `app.py` 与页面对应的 `public/js/`，然后沿调用链进入服务、客户端和持久化。以下为线上维护范围索引；**部分新模块尚不在旧 main 中，缺失时先对齐基线**。

| 问题边界 | 优先检查 | 关键证据 |
| --- | --- | --- |
| 页面/登录/任务恢复 | `public/js/app.js`、对应页面 JS、任务 GET 路由 | 请求是否成功、页面归属、最新任务排序、恢复事件、脚本版本/缓存 |
| 排队、锁、取消、重启恢复 | `api/jobs/`、`api/persistence.py`、ADR-0001/0004 | 任务状态、租约、资源锁、外层记录检查点；不能创建诊断 Worker |
| 飞书字段/分页/权限 | `api/feishu.py`、相关列表/索引服务 | 正确 Base/Table、字段名/类型、游标、缓存与返回码；先投影最少字段 |
| Prompt/文案/模型 | `api/gemini.py`、`api/prompting.py`、`api/services/prompt_configs.py` | 启用版本、目标市场、任务快照、模型响应结构；Prompt 与发布元数据分开 |
| TikHub 商品/库存/视频 | `api/tikhub.py`、对应商品/库存服务 | 商品实际市场、端点、request_id、真实响应结构、有限重试与缓存 |
| 图片/视频转存 | `api/r2.py`、`api/services/doubao_assets.py`、媒体服务 | 源 URL 可读性、内容类型、大小、R2 交付点；不泄露签名 URL |
| 兼职/发布同步 | `api/services/part_time_sync.py`、`publish_sync.py` | 来源记录、成片、元数据、幂等键、人工锁定状态 |
| 账号资格/配额 | `account_product_matcher.py`、`publish_weights.py`（对应基线中） | 国家、参与发布、AI/搬运分类、手动限额、北京时间日期和已提交发布行 |
| 搬运导入/处理/同步 | `video_reuse*.py`、`public/js/video-reuse*.js`（对应基线中） | Excel 绑定、固定计划、资源上限、逐行检查点、发布来源 ID 与账号池隔离 |

可从 `rg --files tests` 查找相关测试，再用 `rg -n '<错误文案或函数名>' api public tests` 缩小范围，不必先读完整仓库。

## 四、常见误判

| 现象 | 先排除什么 | 不要做什么 |
| --- | --- | --- |
| 运行中数字是“—”/刷新后没记录 | 最终结果与实时检查点是否分离、任务 ID 是否只在本机、页面 action 归属、列表排序和脚本缓存 | 直接重新提交整批 |
| 图片 HTTP 403 | 原图/CDN 拒绝访问，和 AI 账号禁用不是同一问题 | 认定模型余额不足、靠充值修图源 |
| Gemini 文案 JSON 不合法 | 已启用渠道/模型、响应文本/结构、字段验证和有限恢复 | 未验证就更换所有 Prompt 或覆盖已有文案 |
| FieldNameNotFound | 表是否重建/迁移、实际 schema 与配置是否一致 | 随意新建同义字段或整批重试写入 |
| TikHub 400/无库存或无图片 | 市场匹配、下架与解析结构、端点通路及有限重试 | 无限重试、将查询失败当库存为零 |
| 成片已完成但没进发布表 | 元数据/审核、账号资格与配额、写入未知结果、来源幂等和回写 | 再编码一遍视频或盲目再创建发布行 |
| 任务慢但 CPU/内存低 | 排队/锁、串行步骤、外部接口与下载等待；测分阶段耗时 | 按机器核数直接放大所有并发 |
| “没有可用账号” | 国家、参与发布、账号分类、日期/名额、人工指定与同商品规则 | 把搬运视频回退到 AI 账号、自动改参与发布勾选 |
| 用户要暂停 | 当前版本是否只有停止；冻结计划是否允许恢复/改方案 | 把取消当无损暂停，或重新导入整份文件造成重复素材 |

## 五、最小复现与验证记录

```text
版本：基线 SHA / 线上 release / 时间与时区
范围：页面、动作、脱敏任务或记录 ID
步骤：最少几次操作可触发
预期 / 实际：
证据：HTTP 状态、脱敏错误码/request_id、检查点、资源窗口
假设与反证：哪些证据支持，哪些仍未知
失败测试：命令 / 修复前结果
修复后测试：命令 / 通过、失败、跳过数量
未验证：真实外部接口、付费、生产写入、上线等分别列出
```

最少样本优先。媒体 URL 只是引用，不下载视频做“全量备份”；不要为排查扫描或导出所有历史表、Cookie 和个人数据。

## 六、需要授权时停在哪

- 缺业务选择、测试数据、源代码基线：更新 Issue，说明缺什么及为什么阻塞。
- 发现密钥曾出现在聊天/日志：视为泄露，通知维护者轮换，不复用或写入文件。
- 需要改飞书字段、清理数据、重试/取消任务、调用付费接口、重启或部署：列出精确目标、影响、费用/风险、回退，先获维护者批准。
- 已批准的修复：按 CONTRIBUTING 做最小改动，写实际证据后提 PR。没有生产验收，最终报告只能写“待上线/待验收”。
