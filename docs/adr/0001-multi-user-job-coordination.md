# ADR-0001：多人使用下的任务协调与幂等

## 状态

Accepted

## 背景

当前后台以单个 Gunicorn Worker 提供 API，并在进程内通过字典和无限制后台线程运行任务。多人使用时存在四类已复现问题：不同批次错误复用同一任务、同一记录跨国家并行覆盖、兼职任务“先查后建”重复创建、Prompt 基于旧内容保存导致后写覆盖。

系统仍以飞书多维表格作为业务数据入口，现阶段不拆分业务微服务，也不迁移历史业务数据。

## 决策

1. Redis 保存持久任务队列、任务状态、精确请求去重键和记录级分布式锁。
2. PostgreSQL 保存兼职同步幂等台账和操作审计日志。
3. 后台任务改为可序列化的 `action + payload`，由固定并发数的 Worker 执行；不再为每次请求创建无限制线程。
4. 精确重复请求按规范化 payload 复用；不同 payload 不复用。所有写同一业务记录的 Action 使用相同资源锁。
5. 兼职任务唯一键为 `来源记录ID + 国家 + 语言`。先预留台账，再写飞书；完成后绑定飞书记录 ID。
6. Prompt 编辑使用内容 revision 做乐观并发控制，旧 revision 返回 HTTP 409。
7. 用户身份继续由后台 Token 鉴权，但支持为每个 Token 配置独立操作者和角色；所有写操作记录操作者。
8. 飞书 GET/PUT 对限流和瞬时服务错误执行有上限的指数退避；非幂等 POST 不盲目重试。

## 影响

### 正面

- 多实例之间也能共享任务状态、去重和锁。
- Web 重启后排队任务仍存在，可恢复执行。
- 同一记录不会被不同国家或不同入口同时写乱。
- 兼职同步和 Prompt 编辑具备明确冲突语义。
- 可追踪谁在何时触发了什么操作。

### 负面

- 新增 Redis 和 PostgreSQL 两个托管依赖。
- 队列提供至少一次执行语义，业务写入仍需幂等保护。
- Redis/PostgreSQL 不可用时，生产写任务必须拒绝进入，不能静默退回不安全模式。

### 中性

- 本地开发在没有外部依赖时使用有界内存后端，但生产环境必须启用持久后端。
- 当前保持单 Web 实例；完成本 ADR 后才允许评估水平扩容。

## 备选方案

- 仅增加 Gunicorn Worker：拒绝。会把内存任务和去重状态进一步分裂。
- 只使用飞书字段做锁：拒绝。飞书没有适合该场景的事务唯一约束。
- 立即拆微服务：拒绝。当前规模下运维成本高于收益。
- 只使用 PostgreSQL 队列：未采用。Redis 更适合阻塞队列和短期分布式锁，PostgreSQL保留强一致台账与审计职责。

## 失败模式与恢复

- Redis 不可用：写任务返回 503；读取业务表仍可用。
- PostgreSQL 不可用：兼职同步、Prompt 写入和需要审计的写任务返回 503。
- Worker 中断：Redis 中未确认任务在租约过期后重新领取。
- 锁超时：任务重新排队，不并行越过锁。
- 飞书限流：安全请求指数退避，超过次数后任务失败并保留错误。

## 回滚

1. Railway 回滚到上一成功部署。
2. 保留 Redis/PostgreSQL 服务和数据，不删除队列及台账。
3. 如新版本尚有排队任务，先暂停 Worker，再回滚 Web。
4. 回滚后只允许单人操作，直到重新部署并发版本。
