# ADR-0004：部署期间批量任务按记录检查点恢复

## 状态

Accepted

## 背景

Web 与后台 Worker 当前运行在同一个 Railway 服务。代码发布时旧容器会退出；Redis 能保留任务，
但运行中的批次只有任务级状态，进程中断后会重新检查整批记录。业务要求失败记录不得自动重试，
同时发布新版本不能丢失或整批重跑正在执行的任务。

## 决策

1. 每条批量记录完成后，将该条结果写入 Redis 检查点；成功、业务拦截和失败结果一视同仁。
2. Worker 恢复同一任务时复用已有检查点，只处理没有结果的记录。
3. 手动“重试失败项”创建新的任务 ID，因此只有用户点击后失败记录才会重新执行。
4. Railway 发布配置启用 `/healthz`、15 秒新旧版本重叠和 130 秒优雅下线。
5. Gunicorn 优雅退出上限为 120 秒，应用最多等待后台 Worker 110 秒；超过后仍由 Redis 租约恢复。

## 影响与权衡

### 正面

- 发布或进程重启后不会丢失排队任务，也不会重跑已有检查点的失败记录。
- 已完成记录无需再次调用飞书或模型接口。
- 新版本通过健康检查后才接收流量，旧版本有时间完成当前工作。

### 负面

- Redis 为每个批量任务额外保存最多一份逐条结果，保留时间与任务记录相同，为 7 天。
- 正在执行但尚未写入检查点的单条记录仍是至少一次执行，业务写入必须继续保持幂等。
- 极长任务超过优雅下线窗口后会由新 Worker 接续，而不是让旧容器无限存活。

## 备选方案

- 只增加 Railway 下线等待：拒绝。批次可能超过等待窗口，仍会整批重跑。
- 失败项自动重试：拒绝。会隐藏真实失败并可能重复消耗模型资源。
- 立即拆分独立 Worker 服务：暂缓。当前规模下新增服务和发布编排成本较高；检查点恢复已满足可靠性要求。

## 失败模式与恢复

- 部署中断：新 Worker 在租约过期后领取原任务，只运行未检查点记录。
- 检查点写入失败：该条在恢复后可能再次执行，由现有记录锁和业务幂等保护。
- 用户主动停止：已完成检查点保留，未开始记录标记为未处理，不自动恢复。
- 业务失败：运行记录显示失败明细，仅在用户点击“重试失败项”后创建新任务。
